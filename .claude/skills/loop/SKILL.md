# 改善ループを1周まわす

規約は [loop.md](docs/00_process/loop.md) の B 節。理由は
[rationale.md](docs/00_process/rationale.md)。

## 回さない条件（先に判定する）

次のどれかに当たったら、**周を始めずに止める**。

| 条件 | 対応 |
| --- | --- |
| 事実がなく印象しかない | まず観測する。`tools/check_docs.py` を回す、時間を測る |
| 測定可能な目標条件が書けない | 書けるまで対象を絞る。書けないなら回さない |
| 直したい対象が2つ以上ある | 周を分ける。**同時に追う改善パスは1本** |
| 対象が「要件」 | ループではなくフェーズ差し戻し。workflow.md に従う |

## 手順

### 1. 現状把握 — 事実だけを集める

```bash
python3 tools/check_docs.py
git log --oneline -20
```

集めるのは事実。**「なんとなく書きにくい」は事実ではない。**

事実の例:
- `TC-012` を書くのに 4 ファイルを行き来した
- 同じ grep を3回打った
- `check_docs.py` が同じ指摘を2周続けて出している
- 同じ種類の修正を今週5回した

### 2. 目標条件を書く — 変更を入れる前に

**測定可能な形で書く。** ここが改善ループの成否を分ける。

| ✕ | ○ |
| --- | --- |
| ハーネスを書きやすくする | TC 1件を書くのに開くファイルを 4 → 2 にする |
| ドキュメントを整理する | `check_docs.py` の指摘を 5 → 0 件にする |
| 手順を楽にする | 同じ grep を打つ回数を 3 → 0 にする（スキルに畳む） |

ユーザーに提示して合意を取る。**この時点で書かれていない目標は、後から書かない。**
変更してから目標を書くと、必ず「達成した」に寄る。

### 3. 障害を1つに絞る

目標条件との差を埋めるのに邪魔なものを列挙し、**1つ選ぶ**。
2つ以上に手を出すと、効いたのがどちらか分からなくなり、学びが残らない。

### 4. 最小の変更を入れる

影響が広範囲に及ぶなら、変更する前に ADR を書く（`adr` スキル）。

よくある変更の落とし先:

| 症状 | 落とし先 |
| --- | --- |
| 同じ手順を2回以上繰り返した | `.claude/skills/` に切り出す |
| 毎回同じルールを言われている | `CLAUDE.md`（ただし長くなるなら skill へ） |
| 同じ確認を手で打っている | `tools/` のスクリプトにする |
| 規約が守られていない | 規約が長すぎるか、理由が書かれていない疑い |

### 5. 検証して、予測の当否を書く

```bash
python3 tools/check_docs.py
```

2節で書いた目標条件を**満たしたかどうかだけ**を判定する。
ついでに良くなったことは書いてよいが、目標条件をそれに差し替えない。

**「予測は外れた」と書ける周は成功。** 学びが残る。
外れたことを書かずに目標条件を後から書き換えるのが、このループが壊れる典型。

### 6. 記録する

[loop_log.md](docs/50_review/loop_log.md) の**先頭**に追記する（新しい周が上）。
書式は [_templates/loop_entry.md](docs/_templates/loop_entry.md)。

**予測の当否の行を空にしない。** ここが空の記録は作業ログであってループ記録ではない。

## 止めどき

- 目標条件を満たした → その周は終わり。次の周をすぐ始めない
- **3周連続で同じ場所を触っている** → ループの問題ではなく設計の問題。
  設計フェーズに戻る判断をユーザーに仰ぐ
- 記録が3周続けて「予測どおり・学びなし」→ 観測の粒度が粗い。1節に戻る
