# コンセプトを掘り出す

## このスキルが守っているもの

`ISS-01`（何を作るか）が全ての前段になっている。ここが曖昧なまま先に進むと、
技術スタックも要件もテストも、全部あとで捨てることになる。

同時に、ここは**ユーザーしか答えを持っていない唯一のフェーズ**でもある。
調べても出てこない。だから聞く。

## 絶対にやらないこと

- **コンセプトを提案で埋めない。** 「こういうアプリはどうですか」と選択肢を並べて
  ユーザーに選ばせるのは、インタビューではなく誘導。ユーザーの中にあるものを出させる
- 答えを聞く前に技術の話をしない
- 「わからない」と言われた項目を、こちらの想像で埋めて先に進まない

## 手順

### 1. 現状を確認する

```bash
cat docs/10_requirements/concept_draft.md
cat docs/10_requirements/open_issues.md
```

既に一部埋まっているなら、埋まっていない項目だけを聞く。

### 2. 掘る

**1 回に 1〜2 問。** まとめて 4 問投げると、どれも浅い答えになる。
答えを聞いてから次を組み立てる。

**聞き方を問いの性質で使い分ける。**

| 問い | 聞き方 | 理由 |
| --- | --- | --- |
| 1〜3（開かれた問い） | **テキストで開いたまま聞く** | 選択肢を出すと、こちらがアプリ案を発明することになり「提案で埋めない」に反する |
| 4〜5（選択肢が実在する問い） | `AskUserQuestion` | 環境や最小形は実在する選択肢から選べる |

聞く順序は固定する。前の答えが次の質問を規定するため。

| # | 聞くこと | なぜ先にこれか |
| --- | --- | --- |
| 1 | 誰のどんな場面のためのものか | ここが決まらないと他の全ての判断基準が無い |
| 2 | いま、その人はどうやって済ませているか | 既存の代替手段。「無い」ことは稀 |
| 3 | それの何が不満なのか | ここが作る理由そのもの。答えられないなら作る理由が無い |
| 4 | 使う場面（PC / スマホ / 常駐 / 一回きり） | ADR-0001 に直結する |
| 5 | 最小で成立する形は何か | スコープの床。「これが無いと意味が無い」の1点 |

**深掘りの合図**: 答えが「便利だから」「あったらいいなと思って」で終わったら、
それは表層。「最後にそれで困ったのはいつ、どういう状況でしたか」と具体で聞き直す。

**自分向けのアプリでよい。** 想定ユーザーが自分1人でも問題ない。
その場合は「自分が」で答えてもらう。無理に一般化させない。

### 3. concept_draft.md に落とす

聞いたことだけを書く。**推測で補間しない。**
埋まらなかった欄は空欄のまま残し、「未確認」と明記する。

「検討したが採らなかった案」の表は、インタビュー中に出て消えた案を必ず書く。
後から同じ案を思いついたときに、一度捨てた理由が残っていると速い。

### 4. スコープの「やらない」を先に埋める

[scope.md](docs/10_requirements/scope.md) の「やらない」を、この時点で最低3つ書く。

**「やる」より先に「やらない」を書く。** やることリストは後からいくらでも膨らむが、
やらないリストは意識して書かないと永遠に空のままになる。

インタビュー中に「それもできたらいいですね」と出た話を、
その場で「やる」に入れずにここへ落とす。

### 5. 必要な調査テーマを洗い出して止まる

コンセプトが埋まったら、次に調べるべきことを
[research/README.md](docs/10_requirements/research/README.md) の一覧に追記する。

**要件（REQ-xxx）の発番はここではやらない。** 調査が終わってからにする。
調査で前提が覆るとID の意味を変えることになり、
[workflow.md](docs/00_process/workflow.md) の「既存 ID の意味を変えない」に違反する。

止まってユーザーに報告する。次は `research` スキル。

## 完了条件

- `concept_draft.md` の「一行で言うと」「誰の何を解決するか」が埋まっている
- `scope.md` の「やらない」に3つ以上ある
- 次に調べるテーマが research/README.md に並んでいる
- 埋まらなかった項目が「未確認」として残っている（空欄のまま放置しない）
