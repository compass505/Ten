# 調査する

## このスキルが守っているもの

調査ノートは**材料**であって決定ではない。ここを混ぜると、
調べているうちに結論が既に出ているような気分になり、選択肢の比較が甘くなる。

材料（`research/`）と決定（`decisions/`）を物理的に分けてあるのはそのため
（[ADR-0004](docs/10_requirements/decisions/ADR-0004-documentation-policy.md)）。

## 手順

### 1. 「この調査で何を決めたいのか」を先に1行で書く

これが書けない調査は、調べても使えない。
書けないなら、まずユーザーに何を決めたいのかを確認する。

対応する `ISS-xx` が [open_issues.md](docs/10_requirements/open_issues.md) にあるか確認し、
無ければ先に起票する。

### 2. 一次情報に当たる

- 検索結果の要約だけで書かない。**公式ドキュメント・原典を WebFetch で読む**
- 「〜と言われている」で終わらせない。誰が言っているかを書く
- 出典は URL とアクセス日を残す。後から検証できない主張は書かない

### 3. 事実と解釈を分けて書く

```markdown
# 調査: <テーマ>

**この調査で何を決めたいのか**: <1行>

調査日: YYYY-MM-DD / → ADR-xxxx

## 1. <観点>
（事実。出典つき）
> 出典: [タイトル](URL)

## この調査から導く結論（→ ADR-xxxx）
（解釈。ここだけが自分の意見）
```

**「この調査から導く結論」以外に自分の意見を混ぜない。**
混ざると、後から読んだときに事実と意見の区別がつかなくなる。

### 4. 選択肢を最低3つ出す

2つだと二択に見えて、実際にはあった第三の道が消える。
「何もしない」「後回しにする」も選択肢として数える。

**採らなかった案の欠点だけでなく、利点も書く。**
利点が書けない案は、そもそも選択肢として検討していない（当て馬）。

### 5. このプロジェクトの制約に照らす

調査結果をそのまま採用しない。既に確定している制約と衝突しないか見る。

```bash
grep -l "ステータス: \*\*Accepted\*\*" docs/10_requirements/decisions/ADR-*.md
```

特に効いてくるもの:
- **ADR-0002**: 乱数・時間・I/O が注入可能でないと採用できない
- **ADR-0004**: ドキュメントを増やす提案は、規約の範囲に収まるか

衝突する場合、それは「調査の結論」ではなく「既存 ADR を覆す提案」になる。
その場合は新しい ADR として起案する必要があるので、明示して止まる。

### 6. 一覧を更新して止まる

[research/README.md](docs/10_requirements/research/README.md) の一覧表に行を足し、
状態を「完了 YYYY-MM-DD」にする。

**決定は下さない。** 結論を ADR の候補としてユーザーに提示して止まる。
確定させるのは `adr` スキル。

## 迷ったとき

- **調査が広がりすぎたら**: 1節に戻る。「何を決めたいのか」に効かない枝は切る
- **結論が出ないとき**: 出ないことを書く。「判断材料が足りない、次に何を調べれば決まるか」
  まで書けば、その調査は成功
- **既存の ADR と衝突したら**: 握りつぶさない。5節に従って明示する
