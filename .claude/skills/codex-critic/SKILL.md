# Codex に反論させる

## なぜ Codex なのか

[ADR-0003](docs/10_requirements/decisions/ADR-0003-improvement-loop.md) の実行ループ段階4
「別文脈のレビュー」の実装。

**同じモデルに自分の書いたものを採点させると、生成時に置いた前提をそのまま正しいものとして通す。**
しかも同一ファミリのモデルは失敗の仕方まで相関するので、Claude のサブエージェントに
Claude の書いた ADR を見せても弱いチェックにしかならない。

別ファミリのモデルに、**明示的に反対側の立場で**読ませる。ここが要点で、
「レビューして」と投げると同意しか返ってこない。「この決定は間違っている、
その理由を挙げろ」と役割を固定する。

## 使いどころ

| タイミング | 渡すもの | 聞くこと |
| --- | --- | --- |
| ADR を Accepted にする直前 | ADR + 元の調査ノート | 選択肢の見落とし、決め手の弱さ、諦めたものの過小評価 |
| 要件を確定させる直前 | requirements.md + scope.md | 判定不能な要件、抜けている異常系、スコープの穴 |
| 基本・詳細設計の DoD 判定前 | 設計 + 要件 | 割り当てられていない要件、閉じていない遷移、IF の不足 |
| テスト項目の DoD 判定前 | cases/ + requirements.md | 要件をなぞっただけの項目、抜けている境界値 |

**実装コードのレビューには使わない。** それは実装フェーズの役割分担で別に定義する
（書く側と検める側を分ける）。

## 手順

### 1. 対象を確定させ、ユーザーに確認する

**外部サービスにドキュメントを送る。** 初回は必ず `AskUserQuestion` で確認する。
同じ対象のループ中は聞き直さない。

送るファイルを列挙して見せる。プロジェクトの中身が外に出ることを明示する。

### 2. 読み取り専用で投げる

**`--write` を付けない。** Codex にファイルを書かせない。
反論を受け取るのが目的で、直させるのが目的ではない。

```bash
CODEX=$(ls ~/.claude/plugins/marketplaces/*/plugins/codex/scripts/codex-companion.mjs 2>/dev/null | head -1)
node "$CODEX" task --effort high "あなたの役割は反対尋問です。同意や要約は不要です。

読んでほしいファイル:
- docs/10_requirements/decisions/ADR-xxxx-....md（確定させようとしている決定）
- docs/10_requirements/research/....md（その根拠にした調査）

このプロジェクトの前提:
- まだ要件定義フェーズで、技術スタックは未確定
- ADR は一度確定させると書き換えない運用（覆すには新規発番が必要）
- 開発者は1人 + AI エージェント

次の観点で、この決定の弱いところを挙げてください:
1. 検討されていない選択肢はあるか
2. 「決め手」として挙げられている理由は、本当に他案を退けるだけの重さがあるか
3. 「結果」で諦めたものを過小評価していないか
4. この決定が前提にしている条件のうち、崩れやすいものはどれか

各指摘について、次を必ず書いてください:
- 具体的にどの記述が問題か（引用）
- それが現実に問題になるのはどういう状況か
- 深刻度（決定を覆すべき / 記述を直すべき / 気にしなくてよい）

同意できる部分をわざわざ書く必要はありません。
根拠のない一般論（「もっと検討すべき」等）も不要です。"
```

`--model` は既定のままでよい。**後戻りコストが特に大きい決定のときだけ**
`--model gpt-5.6-sol` に上げる。

### 3. 指摘を鵜呑みにしない — 3つに仕分ける

**粗を探せと言われたレビュアは、健全なものにも粗を報告する。** これは仕様。
全部に対応すると過剰設計になる。

| 分類 | 見分け方 | 対応 |
| --- | --- | --- |
| **A. 決定を覆す** | 前提が事実と違う、致命的な選択肢の見落とし | ユーザーに報告して止まる。ADR を Accepted にしない |
| **B. 記述を直す** | 決定は妥当だが、理由や結果の書き方が不正確 | ADR を直してから Accepted に進む |
| **C. 却下** | 一般論、このプロジェクトの規模に対して過剰、既に ADR に書いてある | 却下理由を1行添えて報告する |

**C を黙って捨てない。** 却下したことと理由を報告に含める。
そうしないと、次に同じ指摘が来たときに検討済みかどうか分からなくなる。

Codex はこのプロジェクトの規約（ADR-0002 の決定論4条件、ADR-0004 のドキュメント方針）を
知らないので、それらと衝突する提案が混ざる。衝突は C だが、
**「その ADR 自体を見直すべき」という指摘なら A** として扱う。

### 4. 報告して止まる

```
Codex の指摘: N件
├ A（決定を覆す）: ...
├ B（記述を直す）: ...
└ C（却下）: ... ← 却下理由つき
```

**自分で ADR を Accepted にしない。** A / B の有無をユーザーに示して判断を仰ぐ。

## やらないこと

- `--write` を付ける
- Codex の指摘をそのまま全部反映する
- 「指摘なし」を目的にして対象を薄くする
- 同意しか返ってこないプロンプト（「レビューしてください」）で投げる
