## 1. ハーネスの定義

UI・ネットワーク・実時間を経由せず、アプリの中身を**外から駆動して観測する層**。

```
初期状態 + シード + 入力列  →  [ハーネス]  →  [ src の純粋ロジック ]  →  観測できる状態
                                    ↑                                        ↓
                              クロックを引数で進める                  期待値と突き合わせる
```

## 2. 決定論の 4 条件（違反したらレビューで落とす）

| # | 条件 | 具体 |
| --- | --- | --- |
| D1 | 乱数はシードから | `Math.random()` 等をロジック内で直接呼ばない。乱数生成器を引数で受ける |
| D2 | 時間は引数で進む | 現在時刻・経過時間をロジック内で取得しない。`dt` を渡す |
| D3 | I/O は差し替え可能 | 保存・通信・ファイルは口（インターフェース）越し。実装をハーネスが差し替える |
| D4 | 失敗時にシードを吐く | 落ちたテストの出力に、再現に必要な シード + 入力列 が必ず含まれる |

D1〜D3 が守られていれば「同じ入力 → 同じ結果」が成立し、
D4 があって初めて落ちたテストが**デバッグ可能**になる。4 つで 1 セット。

順序を反転させて使う: **D1〜D4 を満たせない設計は、設計が間違っている。**
テストが書きにくいときにハーネスを複雑にするのではなく、`src/` の依存の向きを直す。

## 3. テストの層

| 層 | 置き場 | 対象 | 依存してよいもの | 目安 |
| --- | --- | --- | --- | --- |
| unit | `tests/unit/` | 純粋関数・小さい不変条件 | src の内部 | 即時 |
| **harness** | `tests/harness/` | 入力列を流し込んだ通しの振る舞い | 公開 IF のみ | 秒 |
| e2e | `tests/e2e/` | 実環境での起動・操作 | 実行環境 | 分 |

**主戦場は harness 層。** 要件 `REQ-xxx` の大半はここで担保する。
e2e は「本当に起動して繋がるか」に絞る。数を増やさない。

本数を増やすことが目的ではない。狭いテストを大量に書くより、
入力列を振った通しのシミュレーションを回すほうが効く（→ 調査 1 節）。

## 4. 期待値の書き方

### 4.1 数値を 2 種類に分ける

根拠: [ADR-0012](../10_requirements/decisions/ADR-0012-balance-vs-tests.md)

| 種別 | 中身 | テストに書く | 変え方 |
| --- | --- | --- | --- |
| **要件値** | 要件に書かれている数値。実時間 5 分 / 起動 3 秒 / 相対輝度 0.1 / 10 シード × 10 回 / 実況 3 文以内 / 開始時の山札 1 枚以上 | **書いてよい** | 新しい `REQ-xxx` を発番する |
| **バランス値** | 要件に書かれていない数値。覚醒度の増減量 / 山札の枚数と内訳 / 圧縮率 / 首の可動角度 / 寝たふりの必要時間 / 成功率の減衰 / 段階の粗さ | **期待値に書かない** | **自由に変えてよい。ADR も不要** |

**バランス値は 1 か所に集約する。**コードに散らさない。
データ自体に上下限の表明を持たせ、範囲外は起動時に弾く（表明は期待値ではない）。

### 4.2 種別ごとの書き方

| 使う | 種別 | 使いどころ |
| --- | --- | --- |
| ○ | 例示ベース | **要件値だけで書ける要件**はこれ。入力と期待値を具体値で書く。仕様書を兼ねる |
| ○ | 性質ベース | **バランス値に依存する要件はこれが原則。**下の 5 つの形だけで書く |
| ✕ | 承認 / スナップショット | **使わない。** 期待値の理由が残らず、更新が形骸化する |

性質ベースで使ってよい形は 5 つだけ。

| 形 | 例 |
| --- | --- |
| 比較 | 背中スイッチの上昇量が、その夜の他のどの行動よりも大きい（REQ-015） |
| 単調性 | 覚醒度が低いほど上昇量が大きい（REQ-012） |
| 不変条件 | 元気が下限を割らない。山札の残量が負にならない |
| 存在 | この入力列で親が完全覚醒する / 山札が尽きる（REQ-057） |
| 決定論 | 同じシード・同じ入力列で状態列が一致する（NFR-004） |

確率を含む要件（REQ-017 の成功率）は、**シード集合を固定した統計テスト**で見る。
決定論があるので flaky にならない。

### 4.3 落ちたときの読み方

**バランス値を変えてテストが落ちたら、要件が壊れたということである。実装を直す。**
テストは直さない。バランス値を戻すのでもない。

「正しく動く」は期待値ではない。上の形のどれでも書けないケースは、
テストを無理に書かずに**要件に差し戻す**（要件が曖昧である証拠）。

## 5. 手順（フェーズ 4 → 5）

1. `REQ-xxx` ごとに日本語のテストケース `TC-xxx` を `docs/40_test/cases/` に書く。
   実装を知らない人が読んで合否を判定できる粒度にする
2. `TC-xxx` を `tests/` のコードに落とす
3. **落ちることを確認する。** 落ちないテストは何も検証していない
4. テストをコミットする（実装より先に確定させる）
5. **テストを変更せずに** `src/` を書く
6. green になったら [traceability.md](../40_test/traceability.md) を更新する

### 5.1 空実装の線引き（2026-09-06）

**C# は静的コンパイル言語なので、`src/` に何も無いとテストは「落ちる」のではなく
「ビルドが通らず 1 件も走らない」。**それでは 3 の確認ができない
（12 件が等しく見えないだけで、個々が空振りしていないかは分からない）。

そこで、**フェーズ 4 のうちに `src/` へシグネチャだけの空実装を置く。**

| 置いてよいもの | 置いてはいけないもの |
| --- | --- |
| フェーズ 3 で**確定済みの公開 IF** をそのまま写したシグネチャ | 新しい型・新しいメソッド（設計に無いもの） |
| **`throw new NotImplementedException(...)` の 1 行だけ**の本体 | 条件分岐・計算・戻り値を返す本体（**1 行でも実装なら違反**） |
| 確定済みの列挙型・レコードの定義（types.md にあるもの） | バランス値・定数表 |
| テストのための可視性属性（`InternalsVisibleTo`） | それ以外のインフラコード |

**これは「実装フェーズに入る前にコードを書かない」（CLAUDE.md）の例外ではなく、
その範囲の定義である。**判断を含むものを 1 つでも書いたら違反。

### 5.2 実装前に green になるテストがある

**静的検査系のテストは「実装前は必ず赤」という前提から外れる。**

例: TC-006（`src/` を走査して `System.Random` / `UnityEngine` を参照していないことを見る）は、
空実装の時点で **green になる**。禁止語が書かれていないため。

**これは不具合ではない。**このテストが見張っているのは「実装が環境に触っていないこと」であって、
「実装があること」ではない。**フェーズ 4 の DoD「全て落ちる」は、この種のテストには適用しない。**
どのテストがこれに当たるかは [traceability.md](../40_test/traceability.md) に明記する。

### 禁止

- テストより先に `src/` を書く
- **実装フェーズでテストを書き換えて通す**（バランス調整を理由にしても許さない。
  調整でテストが落ちるなら、それは 4.1 の分類を間違えている）
- 落ちるテストを skip / コメントアウトして先に進む
- バランス値を期待値に書く（4.1）

テストが間違っていると判断した場合は、実装で辻褄を合わせずに**止める**。
要件かテストケースを直し、理由を ADR に残してからテストを更新する。
