# テストファースト / ハーネス規約

種別: リファレンス（規約） — 理由は [rationale.md](rationale.md) に分離
根拠: [調査](../10_requirements/research/test_harness.md) / [ADR-0002](../10_requirements/decisions/ADR-0002-test-harness.md)
状態: **スタック非依存の部分は確定。スタック依存の部分は ADR-0001 待ち**
更新トリガー: ADR-0001 確定時 / ハーネスの書き味に問題が出たとき

---

## 1. ハーネスの定義

UI・ネットワーク・実時間を経由せず、アプリの中身を**外から駆動して観測する層**。

```
初期状態 + シード + 入力列  →  [ハーネス]  →  [ src の純粋ロジック ]  →  観測できる状態
                                    ↑                                        ↓
                              クロックを引数で進める                  期待値と突き合わせる
```

## 2. 決定論の 4 条件（違反したらレビューで落とす）

| # | 条件 | 具体 |
| --- | --- | --- |
| D1 | 乱数はシードから | `Math.random()` 等をロジック内で直接呼ばない。乱数生成器を引数で受ける |
| D2 | 時間は引数で進む | 現在時刻・経過時間をロジック内で取得しない。`dt` を渡す |
| D3 | I/O は差し替え可能 | 保存・通信・ファイルは口（インターフェース）越し。実装をハーネスが差し替える |
| D4 | 失敗時にシードを吐く | 落ちたテストの出力に、再現に必要な シード + 入力列 が必ず含まれる |

D1〜D3 が守られていれば「同じ入力 → 同じ結果」が成立し、
D4 があって初めて落ちたテストが**デバッグ可能**になる。4 つで 1 セット。

順序を反転させて使う: **D1〜D4 を満たせない設計は、設計が間違っている。**
テストが書きにくいときにハーネスを複雑にするのではなく、`src/` の依存の向きを直す。

## 3. テストの層

| 層 | 置き場 | 対象 | 依存してよいもの | 目安 |
| --- | --- | --- | --- | --- |
| unit | `tests/unit/` | 純粋関数・小さい不変条件 | src の内部 | 即時 |
| **harness** | `tests/harness/` | 入力列を流し込んだ通しの振る舞い | 公開 IF のみ | 秒 |
| e2e | `tests/e2e/` | 実環境での起動・操作 | 実行環境 | 分 |

**主戦場は harness 層。** 要件 `REQ-xxx` の大半はここで担保する。
e2e は「本当に起動して繋がるか」に絞る。数を増やさない。

本数を増やすことが目的ではない。狭いテストを大量に書くより、
入力列を振った通しのシミュレーションを回すほうが効く（→ 調査 1 節）。

## 4. 期待値の書き方

| 使う | 種別 | 使いどころ |
| --- | --- | --- |
| ○ | 例示ベース | `TC-xxx` は原則これ。入力と期待値を具体値で書く。仕様書を兼ねる |
| △ | 性質ベース | 不変条件・往復変換・順序非依存など「常に成り立つこと」に限って併用 |
| ✕ | 承認 / スナップショット | **使わない。** 期待値の理由が残らず、更新が形骸化する |

「正しく動く」は期待値ではない。数値・状態・回数で書けないケースは、
テストを無理に書かずに**要件に差し戻す**（要件が曖昧である証拠）。

## 5. 手順（フェーズ 4 → 5）

1. `REQ-xxx` ごとに日本語のテストケース `TC-xxx` を `docs/40_test/cases/` に書く。
   実装を知らない人が読んで合否を判定できる粒度にする
2. `TC-xxx` を `tests/` のコードに落とす
3. **落ちることを確認する。** 落ちないテストは何も検証していない
4. テストをコミットする（実装より先に確定させる）
5. **テストを変更せずに** `src/` を書く
6. green になったら [traceability.md](../40_test/traceability.md) を更新する

### 禁止

- テストより先に `src/` を書く
- 実装フェーズでテストを書き換えて通す
- 落ちるテストを skip / コメントアウトして先に進む

テストが間違っていると判断した場合は、実装で辻褄を合わせずに**止める**。
要件かテストケースを直し、理由を ADR に残してからテストを更新する。
