# 開発プロセス定義

種別: リファレンス（規約） — 理由は [rationale.md](rationale.md) に分離
更新トリガー: フェーズの DoD を満たしても手戻りが起きたとき / フェーズを増減させたとき

ウォーターフォールで段階を踏むが、各段階の内側と、仕組みそのものは
[loop.md](loop.md) のループで回して改善する。

## フェーズ一覧

| # | フェーズ | 成果物 | 完了条件 (DoD) |
| --- | --- | --- | --- |
| 0 | 仕組みづくり | `docs/00_process/` `.claude/` `tools/` | ハーネスの形とループの回し方が決まり、ADR に残っている |
| 1 | 要件定義（調査含む） | `docs/10_requirements/` | 全要件に ID と優先度（Must/Should/Could）。スコープ外が明記されている |
| 2 | 基本設計 | `docs/20_basic_design/` | 全 Must 要件がいずれかのモジュールに割り当て済み。画面/状態遷移が閉じている |
| 3 | 詳細設計 | `docs/30_detailed_design/` | 各モジュールの公開 IF（シグネチャ・型）が確定 |
| 4 | テスト作成 | `docs/40_test/` + `tests/` | 全 Must 要件に対応するテストが存在し、**全て落ちる** |
| 5 | 実装 | `src/` | 全テストが green。通しで動く |
| 6 | 修正改善 | `docs/50_review/` | 出た課題が起票され、対応済み/見送りが判定されている |

フェーズ 0 は 1 より前に一度やるが、以降も並行して更新し続ける（仕組みは固定しない）。

## ID 体系（トレーサビリティの要）

フェーズをまたいで追跡できるよう、最初に ID を振る。

- 要件: `REQ-001`, `REQ-002` ...
- 非機能要件: `NFR-001` ...
- 設計モジュール: `MOD-Xxx` ...
- テストケース: `TC-001` ...
- 決定記録: `ADR-0001` ...

対応表は [../40_test/traceability.md](../40_test/traceability.md) で管理する。
**要件を後から足すときは、必ず新しい ID を発番する（既存 ID の意味を変えない）。**

## フェーズを戻るときのルール

後工程で前工程の欠陥が見つかるのは正常。「黙って実装で辻褄を合わせる」のは禁止。

1. 該当フェーズのドキュメントを直す
2. 理由を `docs/10_requirements/decisions/` に ADR として残す
3. 影響を受けるテストを更新する

## コミット規約

- コミットメッセージ先頭にフェーズを付ける: `[req] 調査結果を追加` / `[test] TC-012 を追加`
- フェーズ完了時にタグを打つ: `git tag phase-1-requirements`
