# ADR-0002: テストハーネスをシード注入型の決定論的ハーネスとする

- ステータス: **Accepted**（2026-08-31 承認）
- 日付: 2026-08-31
- 関連: ISS-03 / [調査: テストハーネス](../research/test_harness.md)

## 背景

「テストファーストで、ハーネス的に」進めたいという方針はあるが、
ハーネスの実体が定義されていない。スタックが未確定（ADR-0001 未着手）なので
ランナーやライブラリは決められないが、**スタックに依存しない部分は先に決められる**。
ここを先に固定しないと、設計フェーズで「テストできない設計」を作り込む。

## 選択肢

| 案 | 利点 | 欠点 |
| --- | --- | --- |
| A. 普通のユニットテストのみ | 準備が要らない。すぐ書ける | 通しの振る舞いと再現性が取れない。「たまに落ちる」を潰せない |
| B. シード注入型の決定論的ハーネス（FoundationDB 型） | 完全再現できる。設計の健全性チェックを兼ねる | 設計に制約が乗る。注入の配線コスト |
| C. 外付けの決定論的実行環境（Antithesis 型） | 既存コードを変えずに済む | 個人開発の規模に対して過剰。新規開発では B の上位互換にならない |
| D. 承認テストで出力を丸ごと固定 | 書くのが速い | 期待値の理由が残らない。新規開発では意味が薄い |

## 決定

**B を採用する。** 決め手は、B の制約（乱数・時間・I/O の注入）が
テストの都合ではなく**設計の健全性の指標そのもの**である点。
注入できない設計はテストできない設計であり、先に弾く価値がある。

確定する規約（スタック非依存）:

1. 決定論の 4 条件 D1〜D4（シード注入 / クロック注入 / I/O 差し替え / 失敗時のシード出力）
2. テストは unit / harness / e2e の 3 層。主戦場は harness 層
3. 期待値は例示ベースを原則、不変条件のみ性質ベースを併用、承認テストは使わない
4. フェーズ 4 の DoD に「全テストが落ちることの確認」を含める
5. 実装フェーズでのテスト書き換えを禁止する

詳細は [test_first.md](../../00_process/test_first.md)。

## 結果

- `src/` の設計は「純粋ロジックが環境に触らない」形に固定される。
  これは後から入れ替えるのが非常に高い（全体の依存の向きに関わる）
- 引き換えに、テスト時に実時間を待たなくてよくなり、ループが速く回る
- モックした振る舞いしか見ないので、実環境との統合は e2e で別途担保する必要がある
- ランナー・乱数実装・入力列の記法は ADR-0001 の後に決める（未決定として残る）

## この決定が崩れる条件

- 注入の配線コストが、テストを書く時間より大きくなったとき
- 作るものが「状態も並行性も順序もほぼ持たない」と要件確定時に判明したとき
  （その場合は A で足りる）
