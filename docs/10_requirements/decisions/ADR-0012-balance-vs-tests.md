# ADR-0012: テストは要件が言っていることだけを検証する（バランス値を期待値に書かない）

- ステータス: **Accepted**（2026-09-02 承認）
- 日付: 2026-09-02
- 関連: ISS-10 / ISU-08 / ISS-06 /
  [ADR-0002](ADR-0002-test-harness.md) 規約 3 と 5 /
  [test_first.md](../../00_process/test_first.md) 4 節・5 節

## 背景

[ADR-0002](ADR-0002-test-harness.md) の規約 5 は
**「実装フェーズでのテスト書き換えを禁止する」**と定めている。
一方、ゲームバランスの数値は触って決めるものであり、実装して遊んでから調整する。

**この 2 つは正面から衝突する。**例示ベースのテストで期待値に数値を固定した後に
バランスを調整すると、テストが落ちる。テストを直せば禁止に触れ、直さなければ調整できない。

Codex が 2026-09-02 に ISU-08 として指摘し、ユーザーが未解決のまま受容した。
以後、**同じ衝突が形を変えて 3 回出ている**（ISU-08 → ISS-10 → ISU-20）。

**今決める必要があるのは、フェーズ 2 で数値を確定させる直前だからである。**
[open_issues.md](../open_issues.md) にも「テスト作成フェーズより前に決着が要る」と書いてある。
ここを越えて数値を決めると、その数値がそのままテストの期待値になり、後から動かせなくなる。

### 決め手になった観察

**確定した要件には、バランスの数値が 1 つも書かれていない。**
Codex の ISU-C1（「値は基本設計」と書くのはテストファーストと逆順である）を却下し、
数値をフェーズ 2 送りにしたときに、要件を全て**性質**で書き直したためである。

- REQ-012「覚醒度について単調非増加」
- REQ-013「少なくとも 1 つを改善し、少なくとも 1 つを悪化させる」
- REQ-017「n が増えるほど下がる。下限は 0 より大きい」
- REQ-015「その夜の他のどの行動よりも大きい」
- REQ-046「残量について単調非増加」
- REQ-056「全ての状態において他より優れていることがない」

**要件が数値を持たないなら、要件を検証するテストも数値を持たなくてよい。**

## 選択肢

| 案 | 利点 | 欠点 |
| --- | --- | --- |
| **A. テストは要件が言っていることだけを検証する（採用）** | **禁止を一切緩めずに衝突が消える。**バランス値を変えてもテストが落ちない。要件と テストが 1 対 1 になり、トレーサビリティが素直になる | 回帰検出力が落ちる。バランス値のタイプミスはテストで捕まらない。テストを読んでも具体的な挙動が分からない |
| B. 不変テストとバランステストに分け、後者だけ書き換え可能にする | 数値も検証でき、回帰を捕まえられる | **書き換えてよいテストという抜け道ができる。**エージェントが詰まったときにそこへ逃げる。禁止の目的（赤 / 緑を曖昧にしない）そのものが壊れる |
| C. バランスをプロトタイプで先に確定させ、実装フェーズでは一切変えない | 数値を期待値に書ける。プロトタイプは ADR-0009 の検証にも要る | 実装後に触って分かることを封じる。期間が延びる。**「触るまで分からない」という前提と矛盾する** |
| D. 実装フェーズでのテスト書き換え禁止を緩める | 素直。調整が自由 | [ADR-0002](ADR-0002-test-harness.md) の核を捨てる。**この禁止は「最も重い違反」として CLAUDE.md にも書いてある** |
| E. 現状維持（衝突を放置） | 何もしなくてよい | テスト作成フェーズで必ず詰まる。4 回目の指摘を待つだけ |

## 決定

**A を採用する。**

決め手は、**A だけが「実装フェーズでのテスト書き換え禁止」を一切緩めずに衝突を消すこと。**
B は抜け道を作り、C は前提と矛盾し、D は禁止そのものを捨てる。

### 確定する規約

**1. 数値を 2 種類に分ける**

| 種別 | 中身 | テストに書いてよいか | 変え方 |
| --- | --- | --- | --- |
| **要件値** | 要件に書かれている数値。実時間 5 分、起動 3 秒、相対輝度 0.1、10 シード × 10 回、実況 3 文以内、開始時の山札 1 枚以上 | **書いてよい** | 新しい REQ を発番する |
| **バランス値** | 要件に書かれていない数値。覚醒度の増減量、山札の枚数と内訳、圧縮率、首の可動角度、寝たふりの必要時間、成功率の減衰、段階の粗さ | **期待値に書かない** | 自由に変えてよい。ADR も不要 |

**2. バランス値は 1 か所に集約する。**コードに散らさない。
`MOD-Board` と `MOD-Sim` が読む単一のデータとして持つ（→ フェーズ 3）。

**3. バランス値に依存する要件のテストは、次の 5 つの形だけで書く。**

| 形 | 例 |
| --- | --- |
| 比較 | 背中スイッチの上昇量が、その夜の他のどの行動よりも大きい（REQ-015） |
| 単調性 | 覚醒度が低いほど上昇量が大きい（REQ-012） |
| 不変条件 | 元気が下限を割らない。山札の残量が負にならない |
| 存在 | この入力列で、親が完全覚醒する / 山札が尽きる（REQ-057） |
| 決定論 | 同じシード・同じ入力列で状態列が一致する（NFR-004） |

確率を含む要件（REQ-017 の成功率）は、**シード集合を固定した統計テスト**で見る。
決定論があるので、統計テストでも flaky にならない。

**4. バランス値を変えてもテストは落ちない。**
落ちたら、それは要件が壊れたということであり、**実装を直す。**

**5. [ADR-0002](ADR-0002-test-harness.md) 規約 5（実装フェーズでのテスト書き換え禁止）は維持する。緩めない。**

## 結果

固定されるもの:

- [ADR-0002](ADR-0002-test-harness.md) 規約 3（「例示ベースを原則、性質ベースは不変条件のみ」）を
  **差し替える。**バランス値に依存する要件では**性質ベースが原則**になる。
  例示ベースは、要件値だけで書ける要件（REQ-007 / 026 / 050、NFR-006 / 008 など）に残る
- [test_first.md](../../00_process/test_first.md) の 4 節（期待値の書き方）と
  5 節（禁止）に、この線引きを追記する。**承認後に行う**
- バランス値のデータ自体に**上下限の表明**を持たせ、範囲外を起動時に弾く。
  これは期待値ではないので、範囲内での調整を妨げない

諦めたもの:

- **回帰検出力。**バランス値のタイプミス（10 を 1 と書く）は、
  上下限の表明に引っかからない限りテストを通ってしまう。
  **これは「バランスが壊れている」のであって「要件が壊れている」のではない**、と割り切る
- **テストが仕様書を兼ねる性質の一部。**性質ベースのテストは、読んでも具体的な挙動が分からない。
  具体像は [game_overview.md](../game_overview.md) と `TC-xxx` の日本語側で担保する
- **面白さはテストの担当ではないことが確定する。**全部 green でもつまらない可能性は残り、
  それはプロトタイプと実プレイでしか判定できない

覆すコスト:

- 現時点ではドキュメントのみ。**テスト作成フェーズに入る前なら安い**
- テストを書いた後に B や D へ移すと、テストの書き直しになる

## この決定が崩れる条件

- **性質だけでは合否を判定できない Must が出てきたとき。**
  その場合、その要件は数値を持つべきであり、**要件側に数値を足して解く**（新 REQ の発番）
- バランス値のタイプミスが実際に見逃され、手戻りが大きかったとき
- 性質ベースのテストが書きにくく、テストを書く時間がかえって増えたとき
- 「バランス値」と「要件値」の線引きが実務で曖昧になり、判断が毎回必要になったとき
