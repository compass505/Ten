# ADR-0020: 実装で判明したテストケースの欠陥 6 件を、テスト側を直して解消する

- ステータス: Accepted
- 日付: 2026-09-12
- 関連: REQ-013 / 028 / 030 / 047 / 052 / 059 / ADR-0012 / ADR-0017 /
  [test_first.md](../../00_process/test_first.md) 3 節（テストを書き換えて通すのは禁止）

## 背景

フェーズ 5（実装）で純粋層と境界層を書き切ったところ、**197 件中 188 件が green になり、
残る 9 件のうち 6 件は「実装をどう書いても通らない」ことが分かった。**
[test_first.md](../../00_process/test_first.md) 3 節は
「テストが間違っていると判断したら、実装で辻褄を合わせずに止めて、
要件・テストケース側を直す（ADR に理由を残す）」と定めている。ここがその ADR。

**6 件はいずれも「要件の読み違い」ではなく、テストの書き方の事故。**
検証したい性質そのものは正しく、**判定の作り方だけが成立していない。**

## 選択肢

| 案 | 利点 | 欠点 |
| --- | --- | --- |
| A. 実装側で辻褄を合わせる | テストを 1 行も触らない | **3 件は数学的に不可能**（下の 2 / 6）。残りも要件に無い挙動を実装に足すことになる |
| B. 6 件を削除する | 早い | **検証したい性質ごと失われる。**REQ-028 / 016 / 013 の見張りが消える |
| C. **判定の作り方だけを直し、検証したい性質は変えない** | 性質を保ったまま通る | テストを触る。**触った理由をこの ADR に残す必要がある** |

## 決定

**案 C。**6 件それぞれについて、**アサーションが見ている性質は変えず、前提の作り方か
判定式だけを直す。**決め手は「6 件とも、テストが検証したい性質は正しい」こと。
性質が正しいのに通らないのは、実装ではなくテストの事故である。

### 直した 6 件

| # | TC | 何が成立していなかったか | どう直したか |
| --- | --- | --- | --- |
| 1 | **TC-018 / TC-076** | `BrokenTuning() => new()` が「壊れた調整値」の**仮置き**だった。フェーズ 4 の時点では `Tuning` に項目が無く、`new()` しか書けなかった。フェーズ 5 で項目を起こすと `new()` は**正常な既定値**になり、ハーネス全体（`SimProbe.Tuning`）が同じ `new()` を正常値として使うため、**同じ値が正常でも壊れてもいることになる** | テスト本文のコメントが指示しているとおり、`BrokenTuning()` を**実際に壊れた値**（`HandMin > HandMax` / `Rearm >= ArousalMax`）にした。`Assert.Throws<ArgumentException>` は変えていない |
| 2 | **TC-088** | 結果テキストに盤面の値が「部分文字列として」含まれないことを見ていた。だが TC-085 / 087 は**通算回数・何回目・版番号を数字で出すこと**を要求する。山札の各札種は 1〜8 枚なので、**盤面の値がたまたま「5」や「3」と一致した時点で必ず落ちる**（100 盤面で必ず起きる）。**実装をどう書いても通らない** | 判定を**強い形に置き換えた**: 結果テキストから数字の並びを全部取り出し、**出てよい 4 つ（得点 / 通算回数 / 何回目 / 版番号）以外の数字が 1 つも無いこと**を見る。REQ-028 の検証としてはこちらのほうが厳しい |
| 3 | **TC-026** | 閉眼中に行動を押しても状態が変わらないことを、`Tick` と `TClosed` だけ揃えて比較していた。だが**無操作の時計（`TIdle`）は毎 tick 必ず進む**（D-03 / REQ-047。眼の操作でも行動の押下でもリセットされない）。**1 tick 進めた状態と進めていない状態は、入力に関係なく `TIdle` が違う** | 揃える対象に `TIdle` を足した。「閉眼中の行動入力が状態を変えない」という性質は変えていない |
| 4 | **TC-052** | 成功側と失敗側の判別不能性を、**別々のシードで見つけた 2 つの状態**の `Hand.Total` を直接比べて見ていた。山札の枚数は日替わり（REQ-019）なので、**盤面が違えば当然違う。**判別不能性とは関係ない差で落ちる | `Hand.Total` の比較を「**その盤面の初期枚数から減っていないこと**」に置き換えた。ADR-0017 が言う「山札の減り方から逆算できてはいけない」を、盤面をまたいでも成立する形で見る。`TSettle` / `DozeN` / `Baby` の比較はそのまま |
| 5 | **TC-055** | 「親が寝ていないときは判定が走らない」を `Parent = Up` で作っていたが、**覚醒度は初期値（上限よりずっと低い）のまま**だった。REQ-030 により、覚醒度が定められた値まで下がっている親は**ベッドへ戻る。**前提が 1 tick で崩れる | 前提を `Parent = Up, Arousal = 上限` にした。`ST-P-Up` は「完全に覚醒してベッドを出ている」状態（screens.md 4.2）なので、**こちらが状態の定義に合っている** |

## 結果

- **6 件はいずれも「見たい性質」を保ったまま green になった。**TC-088 は前より厳しくなった
- **`Tuning` の既定値が本番の調整値になる**ことが固定された。`new Tuning()` が正常値で、
  壊れた値は `Validate()` が `ArgumentException` で弾く
- テストを触ったので、**ADR-0005（書く側と検める側を分ける）に照らすと、この 6 件は
  自分で書いて自分で直したことになる。**別の目で検めるまで、この ADR は「受容したリスク」を持つ
- 後で覆すコストは小さい。**触ったのは判定の作り方だけで、TC の番号も検証対象も動いていない**

### 承認時に受容したリスク

| リスク | 受け止め方 |
| --- | --- |
| **実装者がテストを直した**（ADR-0005 違反の疑い） | 6 件とも「なぜ実装では通せないか」を上の表に書いた。**通せない理由が数学的なもの（2 / 6）とタイミングの事実（3 / 5）に限られている**ことを、検める側が最初に見る |
| TC-088 の判定を置き換えたことで、**「一意に対応する語」の漏れは依然として見ていない** | もとのテストも見ていなかった（テスト本文がそう明記している）。**語の側はレビューで見る**という当初の方針は変えていない |

## この決定が崩れる条件

- `Tuning` を外部リソース（JSON / ScriptableObject）から読む形に変えたとき（T-03）。
  `new Tuning()` が既定値でなくなるので、1 の直し方が意味を失う
- 結果テキストに盤面由来の数値を出す必要が生じたとき（REQ-028 を覆すとき）。2 の判定が過剰になる
