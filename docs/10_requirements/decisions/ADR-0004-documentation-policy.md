# ADR-0004: ドキュメントは「規約」「説明」「決定」の 3 系統に限定する

- ステータス: **Accepted**（2026-08-31 承認）
- 日付: 2026-08-31
- 関連: [調査: ドキュメント体系](../research/documentation.md)

## 背景

土台のディレクトリを作った時点で、ドキュメントに次の穴があった:

- 「なぜこの進め方なのか」がどこにも書かれていない（理由のないルールは破られる）
- 規約と理由が同じファイルに同居していて、規約が読みにくい
- 更新のタイミングが決まっておらず、腐る経路が塞がれていない
- テンプレートが実体と同じ場所にある

一方で、読み手（自分と AI エージェント）がまだ利用者を含まないのに
Diátaxis の 4 分類をそのまま適用すると、空のチュートリアルを量産することになる。

## 選択肢

| 案 | 利点 | 欠点 |
| --- | --- | --- |
| A. Diátaxis 4 分類をそのまま適用 | 体系として完成している | 利用者が存在しない段階では空箱が増える |
| B. リファレンス + 説明 + ADR の 3 系統に絞る | 今の読み手に必要な分だけ。空箱が出ない | 利用者ができた時点で拡張が要る |
| C. 分類しない | 軽い | 規約と理由が混ざり、規約が参照されなくなる |

## 決定

**B を採用する。**

1. **リファレンス**（規約・事実）: `docs/00_process/*.md` ほか各フェーズ。表と箇条書き。理由を書かない
2. **説明**（なぜ）: `docs/00_process/rationale.md`。散文。トレードオフを書く
3. **決定**: `decisions/ADR-xxxx`。不変。覆すときは新規発番

加えて:
- 各規約ファイルの冒頭に**更新トリガー**を書く
- テンプレートは `docs/_templates/` に隔離する
- 繰り返す手順は `.claude/skills/` へ（2 回目に切り出す）
- `CLAUDE.md` は常に効くルールのみ。長くなったら削る
- チュートリアル・ハウツーは**利用者ができてから**書く

詳細は [documentation.md](../../00_process/documentation.md)。

## 結果

- 規約ファイルが短くなり、参照コストが下がった
- 理由が 1 箇所に集まったので、「なぜ守るのか」を毎回説明せずに済む
- 引き換えに、規約を変えるときは規約・説明・ADR の 3 箇所を意識する必要がある
- 利用者向けドキュメントは存在しない状態が続く（アプリが動くまで意図的に空）

## この決定が崩れる条件

- 利用者（自分以外）が現れたとき → チュートリアル・ハウツーを足す
- 「規約はどこ、理由はどこ」を毎回探すようになったとき → 分離が細かすぎる
