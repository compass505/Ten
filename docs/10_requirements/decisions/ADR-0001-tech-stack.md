# ADR-0001: Unity + Android を採用し、物理エンジンを使わない

- ステータス: **Accepted**（2026-09-02 承認）
- 日付: 2026-09-02
- 関連: ISS-02 / [ADR-0002](ADR-0002-test-harness.md) / [ADR-0007](ADR-0007-game-design.md) /
  [調査: アクション化](../research/action_game.md) /
  [調査: 一人称視点](../research/first_person.md)

## 背景

技術スタックはコンセプト待ちで保留されていた。
[ADR-0007](ADR-0007-game-design.md) で「一人称の 3D アクション、Android、2〜3 週間」が
決まったため、**ここで初めて決められる。**

同時に、決めなければならない理由がもう一つある。

**[ADR-0002](ADR-0002-test-harness.md)（Accepted）との衝突である。**
ADR-0002 はシード注入・クロック注入・入力列からの完全再現を確定させているが、

- Unity の `FixedUpdate` は現実時間で一定間隔に呼ばれるものではなく、
  ゲーム内時間で一定にすると定義されている
- Unity 標準の物理は決定論的でなく、決定論的にするには
  deterministic-physics のような別ソリューションの導入が要る

**物理エンジンに乗せた瞬間、ADR-0002 の前提が崩れる。**
スタックの選定と同時に、この扱いを決める必要がある。

## 選択肢

| 案 | 利点 | 欠点 |
| --- | --- | --- |
| A. Unity + 標準の物理エンジン | 実装が最も速い。ぎこちない挙動が自然に出る | **ADR-0002 と衝突する。**覆す ADR の起案が必要になり、ハーネスの守備範囲が縮む |
| B. Unity + 決定論的物理ライブラリ | 物理の表現力と決定論を両立できる | 導入コストが 2〜3 週間には重い。個人開発で扱う難易度が高い |
| **C. Unity + 物理エンジンを使わない（採用）** | **ADR-0002 を覆さずに済む。**座標を自前計算し、固定タイムステップ + 入力列の記録で完全再現できる（格闘ゲームや RTS のリプレイ方式）。表現がぎこちなくなるが、本作では**利点**になる | 物理的な挙動を自分で書く必要がある。凝った表現はできない |
| D. Godot / 独自エンジン | 軽量。ライセンスが緩い | Android 向けの情報量とアセット供給が Unity に劣る。3D の学習コストが読めない |
| E. Web（WebGL / Three.js 等） | インストール不要で共有が容易。Android を選ばない | 3D の手触りと性能が読めない。ネイティブアプリとしての体験にならない |

## 決定

**C を採用する。**

決め手は、**ADR-0002 を覆さずに 3D アクションを成立させられる唯一の組み合わせだったこと。**

A は Accepted の ADR を覆す。B は期間に収まらない。D / E は 3D + Android という
条件に対して情報量とアセット供給で劣る。C だけが、既存の決定を守ったまま成立する。

そして本作は「操作がぎこちないこと」が売りである
（→ [調査: アクション化](../research/action_game.md) 1 節）ため、
高級な物理を捨てることが品質の低下にならない。

### 確定する内容

1. **エンジン**: Unity。**版は 6000.0.83f1（Unity 6 LTS）に固定**（2026-09-07 本人判断）
2. **配布先**: Android（[scope.md](../scope.md) は iOS を除外している）
3. **物理**: Rigidbody / Collider による物理シミュレーションを**使わない**。
   位置と姿勢は自前で計算する
4. **時間**: 固定タイムステップ。実時間を直接読まない（ADR-0002 の D2）
5. **再現**: シード + 入力列（フレーム番号つき）から同じ結果が出ること

## 結果

固定されるもの:

- `src/` の構造が Unity のプロジェクト構成に縛られる
- **ゲームロジックを MonoBehaviour から切り離す必要がある。**
  ADR-0002 のハーネスが素の C# としてロジックを実行できないと、決定論の検証ができない
- Android 向けビルドに Android Studio のインストールと Unity 側の設定が要る
- **Unity 6000.0.83f1（LTS）に固定**（2026-09-07 追記）。
  ADR-0001 は起案時に版を決めていなかったので、環境を作る時点でここに書いた。
  **LTS を選んだ理由**は、長期サポートがあり Android まわりの情報量が多いこと。
  版を上げるときは、盤面仕様の版（REQ-040）とは別に**ハーネスの再実行で確かめる**
  （NFR-004 が版に依存しないことの確認）

諦めたもの:

- 物理エンジンによるリアルな挙動と、それに伴う偶発的な面白さ
- iOS 対応（配偶者の端末が iOS の場合、**この決定は見直しになる。未確認**）
- Web での手軽な共有

覆すコスト:

- エンジンの変更は実装フェーズに入った後だと全損に近い
- 物理エンジンの解禁は、ADR-0002 を覆す新規 ADR の起案が必要

## この決定が崩れる条件

- **配偶者の端末が iOS だと判明したとき。**夫婦で遊ぶ以上、片方が遊べないなら成立しない
- 自前の運動計算では「ぎこちないが気持ちよい」手触りが出せないと判明したとき
- Unity のビルド環境の構築だけで期間の大半を消費すると判明したとき
- ADR-0002 が別の理由で覆されたとき（その場合 A が選択肢に戻る）

## 承認時に受容したリスク（2026-09-02）

[Codex レビュー](../../50_review/issues.md)の指摘を未解決のまま、
ユーザー判断により Accepted とした。**特に下 2 件は期間に直結する。**

- **ISU-07**: **開発者は Unity / C# / Android 実機ビルドがほぼ未経験**
  （2026-09-02 確認）。この場合、情報量やアセット供給の多さより、
  **学習・設定・デバッグ時間が工数を支配する。**採用理由の前提が弱い
- **ISU-09**: **2〜3 週間という見積もりに根拠が無い。**
  調査自身が「2〜3 週間 / Unity 3D アクション / ADR-0002 の決定論は
  同時に満たせない可能性が高い」と書いている
- **ISU-06**: **配偶者の端末が iOS か Android か未確認のまま Android 専用を決めた。**
  iOS だった場合、「夫婦で同じ盤面を比較する」というコンセプトの必要条件が壊れる
- **ISU-08**: [ADR-0002](ADR-0002-test-harness.md) の「実装フェーズでのテスト書き換え禁止」と、
  未確定のゲームバランスが衝突する。例示テストで期待値を固定した後に
  バランス調整すると、禁止に触れるか調整不能になる。**未解決**
- **ISU-17**: 「物理エンジンを使わない」は範囲が広すぎる。
  物理を演出・入力ヒットテストに限定し勝敗判定に使わない構成なら両立できる
- **ISU-18**: 「完全再現できる」の再現範囲が未定義。
  タッチ座標・解像度・フレーム境界・浮動小数点・端末差の正規化が要る
