# 調査: 開発ループ / 仕組みの改善

**この調査で何を決めたいのか**: 「仕組みづくりをループで改善する」の 1 周を何にするか。
何をトリガーに回し、何を観測し、いつ止めるか。

調査日: 2026-08-31 / → [ADR-0003](../decisions/ADR-0003-improvement-loop.md)

---

## 1. 2 種類のループを混ぜない

調べると「ループ」と呼ばれているものが 2 つあり、性質が違う。混ぜると事故る。

| | 実行ループ | 改善ループ |
| --- | --- | --- |
| 目的 | 決まった仕様を満たすまで回す | 仕組み自体を良くする |
| 1 周 | 実装 → 検証 → 修正 | 観測 → 仮説 → 変更 → 検証 → 記録 |
| 終了 | チェックが green | 目標条件を満たした / 学びが尽きた |
| 頻度 | 分〜時間 | 日〜フェーズ単位 |
| 危険 | 通すためにテストを書き換える | 事実なしに印象で回し続ける |

**実行ループは自動化してよい。改善ループは人間が判断を持つ。**

---

## 2. 実行ループ: 検証で閉じる

Claude Code のベストプラクティスが繰り返し言っているのは
「**エージェントが自分で走らせられるチェックを与えろ**」という一点。
チェックがないとエージェントは「done に見えたら止まる」ので、人間が検証ループになる。

チェックの強さには段階がある:

| 段階 | 手段 | 性質 |
| --- | --- | --- |
| 1 プロンプト内 | 「実装したらテストを走らせて直せ」と同じ指示に書く | 準備ゼロ。今日から効く |
| セッション横断 | `/goal` に達成条件を置く。毎ターン別の評価器が判定 | 放置できる |
| 決定論的ゲート | Stop フック。スクリプトが通るまでターンを終わらせない | 例外なく効く |
| 別視点 | レビュー用サブエージェント。実装した文脈とは別の文脈で差分を見る | 自己採点を防ぐ |

「成功した」と言わせるのではなく、**証拠（テスト出力・実行したコマンドと戻り値）を出させる**。

避けるべきとされる典型:
- 無関係なタスクを同じ文脈に混ぜる（→ 区切る）
- 同じ指摘を 2 回して直らなければ、文脈が汚れている（→ 文脈を捨てて指示を書き直す）
- 検証できないものを完了扱いにする

> 出典: [Best practices for Claude Code](https://code.claude.com/docs/en/best-practices)

## 3. 改善ループ: 仮説と目標条件を先に書く

PDCA と Improvement Kata（トヨタカタ）を見ると、有効なループに共通しているのは
「**回す前に、何がどうなれば成功かを測定可能な形で書く**」こと。

Improvement Kata の 1 周:

```
方向性 → 現状の把握 → 目標条件 → 障害の列挙 → 小さい実験 → 現状の再把握
```

要点として挙げられていたもの:

- 議論を **1 本の改善パスに絞る**。同時に複数を追わない
- 目標条件は**測定可能**にする。「良くする」は目標条件ではない
- 変更は**小さく**、リスクを限定した試行として入れる
- Check の段階で「**予測が当たったかどうかを明示的に述べる**」。
  これをやらない PDCA は、ただの作業ログになる
- ゆるい ToDo リストではなく、**学習ループ**として回す

> 出典:
> - [Improvement Kata Retrospective](https://jeda.ai/ai-templates-frameworks/ai-improvement-kata-retrospective)
> - [PDCA cycle — Tempo](https://www.tempo.io/glossary/pdca-cycle)
> - [Toyota Kata — Methods & Tools](https://www.methodsandtools.com/archive/toyotakata.php)

## 4. 仕様を中心に置く流れ（spec-driven development）

2025 年末に GitHub Spec Kit が広め、2026 年には主要ツールが同様の形を持つようになった流れ。
仕様を「受け身の説明書」ではなく「**実行される契約**」として扱い、そこからコードを導く。

Spec Kit のフェーズ:

```
constitution（原則）→ specify（何を）→ plan（どう）→ tasks（分解）→ implement → converge（仕様との突合）
```

良い仕様が固定するものとして挙げられていたもの:
**成果 / スコープ境界 / 制約 / 既存の決定 / タスク分解 / 検証基準**。
仕様が書き落とした部分はエージェントが勝手に埋めるので、書き落としがそのまま事故になる。

Claude Code 側にも対応する手順がある: 大きめの機能では、まずエージェントに
**こちらをインタビューさせて仕様を書かせ**、仕様が固まったら文脈を新しくして実装に入る。
自己完結した仕様（関係するファイルと IF の名前・スコープ外・末尾に end-to-end の検証手順）が
最も効く、とされている。

これは既に `docs/00_process/workflow.md` のフェーズ制とほぼ同型。
**新しく導入するものではなく、既存のフェーズ制が正しかったことの裏付けとして扱う。**

> 出典:
> - [GitHub Spec Kit](https://github.com/github/spec-kit)
> - [Spec-Driven Development in 2026 — Devoteam](https://www.devoteam.com/expert-view/spec-driven-development-2026/)
> - [Best practices for Claude Code](https://code.claude.com/docs/en/best-practices)

## この調査から導く結論（→ ADR-0003）

1. ループを **実行ループ**と**改善ループ**に分けて別々に定義する。
2. 実行ループは「チェックが green になるまで」。チェックは自動で走るものに限る。
   自動化の段階は 1 プロンプト → Stop フックの順で、必要になってから上げる。
3. 改善ループは 1 周につき **測定可能な目標条件**を先に書く。書けない周は回さない。
4. 記録には「予測が当たったか」を必ず書く（`loop_log.md` の書式に入れる）。
5. 同時に追う改善パスは 1 本。
