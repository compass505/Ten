# 調査: ドキュメント体系

**この調査で何を決めたいのか**: どのドキュメントを、どこに、どういう単位で書くか。
何を書かないか。いつ更新するか。

調査日: 2026-08-31 / → [ADR-0004](../decisions/ADR-0004-documentation-policy.md)

---

## 1. Diátaxis: ドキュメントを 4 種に分ける

技術文書の分類として広く使われている枠組み。**混ぜるな**、が本質。

| 種別 | 読む状況 | 性格 |
| --- | --- | --- |
| チュートリアル | 学ぶために手を動かす | 手を引いて連れて行くレッスン。成功が保証されている |
| ハウツーガイド | 仕事のために手を動かす | 目的から逆算した手順。前提知識を要求してよい |
| リファレンス | 仕事中に参照する | 事実のみ。中立。構造は対象の構造に従う |
| 説明 | 理解するために読む | なぜそうなっているか。背景・トレードオフ |

2 つの軸で整理される:

```
              行動（doing）        認識（knowing）
学習（study）  チュートリアル       説明
仕事（work）   ハウツーガイド       リファレンス
```

**導入の仕方**: 全部を一度に整えない。今あるドキュメントを見て、1 つだけ小さく直す。
それを繰り返す。直すたびに次に直すべき場所が見えてくる、という進め方が推奨されている。

**この 4 分類が効くのは「読み手がいるドキュメント」。**
今回のように読み手が自分（と AI エージェント）である開発中プロジェクトでは、
そのまま当てはめると空のチュートリアルを量産することになる。分類は借りるが、
**当面はリファレンスと説明の 2 種だけで足りる**、という判断が要る。

> 出典: [Diátaxis](https://diataxis.fr/) / [Start here](https://diataxis.fr/start-here/)

## 2. ADR: 決定を 1 件 1 ファイルで残す

Michael Nygard が 2011 年に広めた軽量な形式。**背景 / 決定 / 結果（consequences）**が骨。
1 件の決定と、その理由・トレードオフ・結果を捉える。集まると決定ログになる。

実務上効いているとされる運用:
- 連番で採番する
- 確定した ADR は書き換えない。覆すときは新しい ADR を切り、旧 ADR を
  `Superseded by ADR-xxxx` にする
- コードと同じリポジトリに置く（決定とコードが一緒に古びるのを防ぐ）

ADR が要るのは「**後から理由を思い出せないと困る決定**」だけ。
可逆で安い決定に ADR を書くと、決定ログがノイズで埋まる。

> 出典: [adr.github.io](https://adr.github.io/)

## 3. 仕様をリポジトリに置く流れ

Spec Kit は `.specify/`（テンプレート）と `specs/`（仕様の実体）を分けて置く。
原則（constitution）→ 仕様 → 計画 → タスク、と粒度で階層化されている。

参考になるのは**構造の考え方**であって、ディレクトリ名ではない:

- 変わらないもの（原則・規約）と、変わるもの（個別の仕様）を分ける
- テンプレートを実体と分けて置く
- 仕様は自己完結させる。読むのに会話履歴が要る仕様は仕様ではない

Claude Code 側の対応する助言:
- `CLAUDE.md` は**毎回読み込まれる**ので、常に効くものだけを書く。短く保つ。
  各行について「これを消したら間違いが起きるか？」を問い、起きないなら消す
- 長すぎる `CLAUDE.md` は無視される（重要な指示がノイズに埋もれる）
- **たまにしか要らない知識・手順はスキル（`.claude/skills/`）に出す**。
  必要なときだけ読み込まれる
- 「2 回繰り返した手順はスキルにする」という目安

> 出典:
> - [GitHub Spec Kit](https://github.com/github/spec-kit)
> - [Best practices for Claude Code](https://code.claude.com/docs/en/best-practices)

## 4. ここから見た現状の穴

土台を作った時点のドキュメントを上の観点で点検した結果:

| 穴 | 内容 |
| --- | --- |
| 説明（explanation）が無い | 「なぜこのフェーズ制か」「なぜハーネスか」がどこにも書かれていない |
| リファレンスと説明が混ざっている | `workflow.md` に規約と理由が同居している |
| 更新のタイミングが決まっていない | 誰がいつ直すのかが無いドキュメントは必ず腐る |
| テンプレートと実体が同じ場所にある | ADR テンプレートが ADR 本体と同じディレクトリにある |
| 読み手が定義されていない | 自分 / 未来の自分 / エージェント のどれ向けかで書き方が変わる |

## この調査から導く結論（→ ADR-0004）

1. Diátaxis の 4 分類のうち、当面は**リファレンスと説明**のみを使う。
   チュートリアル・ハウツーはアプリが動いてから（利用者ができてから）書く。
2. 1 ファイル 1 役割。規約（リファレンス）と理由（説明）を同じファイルに混ぜない。
3. 決定は ADR に集約。ADR は不変。覆すときは新規発番。
4. `CLAUDE.md` は「常に効くルール」だけ。手順はスキルに出す。2 回繰り返したら切り出す。
5. 各ドキュメントに**更新トリガー**（何が起きたら直すか）を明記する。
